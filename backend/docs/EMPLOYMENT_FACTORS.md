# Employment Factors Post-Processing

This backend derives direct employment results after an OSeMOSYS simulation has
finished. The calculation is ex-post: it does not affect the optimization
objective, constraints, solver status, or feasibility.

## Source Data

Employment factors originate in:

```text
https://github.com/DEA-GE/colombia-employment-factors
```

The backend uses:

```python
from colombia_employment_factors import (
    get_model_employment_factors,
    get_technology_assumption,
)
```

The package API dependency is pinned to commit
`a0aed31f75844cc1af32e67318de5037b3f46f9d`. The data used by this backend are
the explicit, checksum-verified snapshot under
`app/data/employment_factor_snapshot/`, passed to those APIs using their
existing optional path arguments. They do not depend on a moving branch or
on whichever packaged CSV happens to be installed locally.

The snapshot is a targeted integration of the canonical PCH/SMR build (input/code
revision `ac165f703e0a7361148a6c13a0abc8552919a16b`) and the frozen pre-change PR
snapshot. Its `targeted_refresh` metadata identifies both parents and the two
replaced/added catalogue technologies. Every unrelated baseline row is retained,
including wind, rooftop solar and their previous productivity choices. The
dependency pin identifies the published canonical artifact commit. The build-time dirty flag includes
generated files awaiting that artifact commit; it does not imply uncommitted
methodology inputs. No manifest attempts to embed its own enclosing commit SHA.
The generated-data checksum identifies the actual consumed factors.

`get_model_employment_factors(snapshot_path)` provides yearly employment factors for
2024-2055. The factors have already been projected by the package methodology,
including decline/productivity assumptions where applicable.

`get_technology_assumption(technology, snapshot_path)` provides:

- `construction_time_years`
- `lifetime_years`
- source metadata for those assumptions

The current backend uses construction time for annualizing construction and
manufacturing employment. Lifetime is retained in row metadata for traceability
and future lifecycle metrics, but it is not used in the main in-horizon outputs.

## Technology Mapping

The runtime mapping lives in:

```text
backend/app/services/employment_factors_mapping.yaml
```

Each OSeMOSYS technology maps to one or more employment-factor technologies.
The seven configured regional prefixes `AN`, `CA`, `IN`, `NE`, `OR`, `SE`, `SO`
expand to the same components (for example `AN_PWRSOLRTP`). Technology names and
region identifiers remain distinct in results; no regional employment is summed
merely because it shares a canonical factor.
The `multiplier` field is the MW of employment-factor technology represented by
one MW of model technology.

Example:

```yaml
PWRSOLUGE_BAT:
  components:
    - employment_technology: Utility-scale solar PV
      multiplier: 1.0
    - employment_technology: Battery storage (grid)
      multiplier: 0.6
```

For `PWRSOLUGE_BAT`, one MW of model capacity is treated as one MW of
utility-scale solar PV plus 0.6 MW of grid battery storage. The component
employment values are summed into one output row for the model technology, while
component metadata remains available in `index_json`.

## Input Capacity Variables

Only model-period installations from 2025 onwards are counted.

`NewCapacity` is used for construction and manufacturing:

```text
Employment_FTEyear_ConsManu_Direct =
    NewCapacity_MW * Construction&Manufacturing direct factor
```

`AccumulatedNewCapacity` is used for O&M:

```text
Employment_FTE_OM_Direct_Annual =
    AccumulatedNewCapacity_MW * O&M direct factor
```

`TotalCapacityAnnual` is intentionally not used for employment factors. It
includes residual capacity from the last historical year, 2024. Using it would
estimate O&M employment for the whole installed system, while this workflow
estimates employment generated by capacity additions from the optimization
period.

## Unit Conversion

OSeMOSYS capacity outputs in this repository are treated as `PJ/year`. The
employment factors use MW. Capacity is converted before applying factors:

```text
1 GW = 31.5576 PJ/year
MW = PJ/year * 1000 / 31.5576
```

## Unit Harmonization

Raw construction/manufacturing and O&M outputs are not directly comparable:

| Phase | Factor unit | Output after multiplication | Interpretation |
|---|---:|---:|---|
| Construction and manufacturing | FTE-year/MW | FTE-year | One-off labor attached to a construction cohort |
| O&M | FTE/MW | FTE | Annual workforce sustained by operating capacity |

For annual employment charts, construction/manufacturing FTE-years are spread
uniformly over the construction period from the technology assumptions package.
O&M is already annual and is not annualized.

For a plant commissioned in year `y` with construction time `d`:

```text
construction interval = [y - d + 1, y]
annual C&M FTE during construction = C&M FTE-year / d
```

The implementation supports fractional construction times. It allocates C&M
employment according to the fraction of the construction interval overlapping
each model year. The allocated annual values sum back to the original C&M
FTE-year total.

Example with an integer construction time:

```text
Commissioning year: 2030
C&M labor: 1,000 FTE-year
Construction time: 5 years

Annualized C&M FTE:
2026: 200
2027: 200
2028: 200
2029: 200
2030: 200
```

For early model-period commissioning years, some construction effort can fall
before 2025. The main annual chart keeps only in-horizon years. Pre-2025
construction labor is stored separately as:

```text
Employment_FTEyear_ConsManu_Direct_PreHorizon
```

This avoids silently dropping the labor while also avoiding the creation of
fake historical annual model outputs.

## Persisted Variables

Derived rows are stored in `osemosys.osemosys_output_param_value` with the same
simulation job id as the rest of the model outputs.

The employment variables are:

```text
Employment_FTEyear_ConsManu_Direct
Employment_FTE_ConsManu_Direct_Annualized_InHorizon
Employment_FTEyear_ConsManu_Direct_PreHorizon
Employment_FTE_OM_Direct_Annual
Employment_FTE_Total_Direct_Annual_InHorizon
Employment_FTEyear_OM_Direct_Cumulative_InHorizon
Employment_FTEyear_Total_Direct_Cumulative_InHorizon
```

### Variable Meanings

`Employment_FTEyear_ConsManu_Direct`

: Original direct construction/manufacturing result in FTE-year, attributed to
  the commissioning year of `NewCapacity`.

`Employment_FTE_ConsManu_Direct_Annualized_InHorizon`

: Direct construction/manufacturing annual FTE allocated over construction
  years that are inside the model horizon.

`Employment_FTEyear_ConsManu_Direct_PreHorizon`

: Direct construction/manufacturing FTE-year associated with model-period
  capacity additions but allocated before 2025 by the construction-time spread.

`Employment_FTE_OM_Direct_Annual`

: Direct annual O&M FTE from cumulative new capacity in each model year.

`Employment_FTE_Total_Direct_Annual_InHorizon`

: Annual comparable direct employment:

```text
Employment_FTE_ConsManu_Direct_Annualized_InHorizon
+ Employment_FTE_OM_Direct_Annual
```

`Employment_FTEyear_OM_Direct_Cumulative_InHorizon`

: Cumulative in-horizon direct O&M FTE-year, calculated as the running sum of
  annual O&M FTE over model years.

`Employment_FTEyear_Total_Direct_Cumulative_InHorizon`

: Cumulative in-horizon direct total FTE-year, calculated as the running sum of
  total annual direct FTE over model years.

## Dimensions and Disaggregation

Employment rows remain disaggregated by:

- simulation job;
- region;
- model technology;
- year;
- employment variable;
- job type;
- phase/factor type.

Composite technologies keep component metadata in `index_json`, including:

- employment-factor technology;
- component multiplier;
- converted component capacity in MW;
- factor value and unit;
- factor source;
- construction time and lifetime assumptions;
- construction allocation metadata for annualized C&M rows.

This allows downstream charts to show either:

- model-technology totals, such as `PWRSOLUGE_BAT`; or
- component details, such as solar PV and grid battery contributions inside
  `PWRSOLUGE_BAT`.

Every persisted employment row also carries compact
`employment_factor_provenance` in `index_json`: source revision/content hash,
factor-table checksum, scenario, productivity assumption and solar readiness.
No database schema migration is required. Duplicate model-factor keys, missing
mapped factors, unsupported units and non-finite/negative factors fail explicitly.
Non-power technologies without a mapping remain outside this calculation.

## Reporting Guidance

Use `Employment_FTE_Total_Direct_Annual_InHorizon` for annual employment charts.
It is the comparable annual FTE metric.

Use `Employment_FTEyear_Total_Direct_Cumulative_InHorizon` for milestone charts
such as cumulative employment by 2030, 2035, or 2040.

Keep `Employment_FTEyear_ConsManu_Direct` available for audit because it is the
direct output of multiplying `NewCapacity` by the construction/manufacturing
factor before annualization.

Current reporting uses annual model years. Summing annual FTE over one-year
intervals gives FTE-years; divide by the interval duration for an average annual
workforce. Irregular/representative years require an explicitly approved period
weighting convention and must not be interpreted as annual consecutive years.
O&M uses current-year factors on surviving new-build capacity, not vintage
factors or residual/historical capacity. These conventions are unchanged.

## Regeneration, comparison and current gaps

The source repository's `docs/methodology.md` documents input extraction,
six solar transfer ratios, category boundaries and selective productivity policy.
The chosen 0.32 ratio is an approximate modelling assumption; its exact inverse
is 3.125. It is not applied to Colombia I-JEDI, its derived rooftop factors,
already-LATAM factors, global manufacturing or nuclear O&M.

**Current solar status:** the full-precision US utility run is missing. The six-ratio
implementation is tested, but the published rooftop series remains exactly
unchanged and is explicitly labelled pending. Rounded screenshots are not used
as production factors. Conventional Nuclear remains available; the existing PWRNUC code now uses the
separate SMR proxy source documented below.

After an approved source build, run from the OSeMOSYS repository root:

```sh
python backend/scripts/sync_employment_factor_snapshot.py --source-dir ../colombia-employment-factors/data/processed
python backend/scripts/compare_employment_factors.py --baseline-workbook employment_results_PD_CN_PA.xlsx --old-factors ../colombia-employment-factors/data/audit/baseline_model_default_23b7f592.csv --output-dir backend/reports/employment_methodology/central
```

The comparison replays the same observed capacity cells with old/new factors
through the runtime calculation service. `factor_comparison.csv` includes
absolute/percentage changes; `employment_comparison.csv` preserves scenario,
technology, region, year, phase-specific variable and units. Undefined percentage
changes from a zero baseline remain blank. Summaries add only construction
cohort FTE-years; annual and cumulative rows are never added together.

The preserved workbook contains 2,999 blank capacity cells, including historical
years. The replay excludes them consistently and lists them in
`unobserved_capacity_cells.csv`, without substituting zero. The original scenario
exports are unavailable, so completeness of the original solver output cannot
be independently restored. No new optimisation, solver licence or database is
needed for this factor comparison.

`--new-factors PATH` selects an isolated scenario factor CSV for comparison.
The source repository builds low/high employment-intensity cases and a
`--productivity-transfer none` source-refresh reference. Runtime sync accepts
only central/selective/catalogue builds. This keeps sensitivities out of the
default runtime data.

To rebuild the existing workbook report from preserved inputs:

```sh
python backend/scripts/build_employment_results_workbook.py --baseline-workbook employment_results_PD_CN_PA.xlsx --output employment_results_methodology_review.xlsx
```

It refuses to overwrite the input baseline. Construction and O&M output units
are explicit. It generates the six base sheets, not additional manually maintained
baseline pivot/display sheets. Formula-based workbooks require Excel recalculation; CSV replay
outputs are computed directly in Python. No native Excel cache validation is
claimed.

For a separate source rebuild, use `--output-dir PATH` in the factor builder,
then run `backend/scripts/validate_employment_factor_delivery.py --source-repo
../colombia-employment-factors --rebuild-dir PATH` from the OSeMOSYS repository.
This verifies input/output hashes, packaged copies, deterministic regeneration,
sensitivity ordering and deliberately unchanged technology factors.

Rollback restores the prior source/data snapshot and matching checksum manifest
through reviewed revert changes. Original workbooks, the baseline results
workbook contents are preserved. Do not reset branches.

## PCH/SMR update and targeted PR #174 snapshot

The confirmed SMR generating code is `PWRNUC`, also explicitly labelled
"Nuclear power plant (SMR)" in SAND `SETS!B41:C41`. Its employment category is
now `SMR`, using `Rutovitz 2015 (SMR proxy)`; conventional `Nuclear`
remains in the catalogue. All seven regional prefixes inherit this correction.

| Model code | Before | After | 2024 C+M before → after | 2024 O&M before → after |
| --- | --- | --- | ---: | ---: |
| PWRHYDROR | Hydro (small), legacy selective | Hydro (large), retained selective | 62.80655 → 27.74325 | 15.955625 → 0.6252 |
| PWRHYDROR_NDC | Hydro (small), legacy selective | Hydro (small), calibrated | 62.80655 → 9.66 | 15.955625 → 0.8 |
| PWRNUC | Nuclear | SMR, conventional-nuclear proxy | 20.9 → 13.1 | 1.15 → 0.6 |

C+M is FTE-years/MW; O&M is annual FTE/MW. The raw legacy small-hydro
coefficients are 15.8 construction, 10.9 manufacturing and 4.9 O&M.
Interpolation gives 2024 O&M 5.1058; the prior PR selective multiplier gives
5.1058/0.32 = 15.955625. The new source starts in 2024 at 7.36/2.30/0.8;
C+M is calculated once as 9.66. Neither the old interpolation uplift nor the
extra productivity multiplier applies to this calibrated source. Subsequent
years retain small-RoR catalogue CAPEX/OPEX projections, holding 2050 through 2055.

The new PCH source combines reported generic hydro C/M coefficients from
Rutovitz et al. (2025), Table 3 p.4, with analyst-selected O&M of 0.8.
ESMAP (2023) provides an 80-MW scale benchmark of approximately 50 forecast
operating staff; 50/80 = 0.625 employees/MW is calculated, and 0.8 is not an
ESMAP published coefficient. Provisional low/base/high O&M values are
0.3/0.8/1.5; only base is executable. This is a proxy for MW-scale PCH, requiring
validation against Colombian projects and their automation/shared staffing.

PEN Tomo II p.69 distinguishes small RoR 1–20 MW and mini <1 MW. The agreed
model classification is supported by cost correspondence: the CSV inputs for
PWRHYDROR match large RoR catalogue costs closely, while PWRHYDROR_NDC matches
small RoR costs closely. This is evidence about the aggregate model classes,
not confirmation of every constituent plant's capacity. NDC dispatch status
does not imply micro/mini scale; the unsupported "very small" note was removed.
PWRHYDDAM is unchanged. The project team approved these class assignments.

The SMR phase factors 11.8/1.3/0.6 are conventional nuclear OECD coefficients
from Rutovitz, Dominish and Downes (2015), Table 1 p.5, deliberately transferred
as unvalidated SMR proxies. They are constant throughout 2024–2055 and have no
new learning rate or productivity multiplier. C+M is 13.1. The old catalogue
Nuclear source uses higher Latin America values (19.6/1.3/1.15); consequently,
this implementation changes numerical SMR outputs. It does not force a
difference merely for classification. Employment scheduling uses the SMR
datasheet's 2030 D10/D11 assumptions: 40-year lifetime and 8-year construction.
Energy-system operational lifetime and other inputs remain unchanged.

The canonical default has evolved since the PR's baseline. A wholesale snapshot
replacement would change unrelated factors, including wind. The targeted sync
therefore takes only Hydro (small) and SMR from the new canonical artifact and
retains all other baseline factors and assumptions exactly. Its
`targeted_refresh` provenance identifies the baseline manifest, replacement
tables, source revision and technologies. The top-level legacy productivity and
solar settings describe retained rows; the targeted replacements explicitly use
no extra productivity transfer. The result provenance exposes this distinction.
Existing wind references, mappings, projections, factors and employment outputs
remain unchanged.

### Reproduction and evidence

Run from the OSeMOSYS repository using an environment with the pinned package,
pandas, openpyxl and PyYAML installed:

```sh
python backend/scripts/sync_employment_factor_snapshot.py --source-dir ../colombia-employment-factors/src/colombia_employment_factors/data --baseline-dir backend/reports/employment_methodology/pch-smr/baseline
python backend/scripts/compare_employment_factors.py --baseline-workbook employment_results_PD_CN_PA.xlsx --old-factors backend/reports/employment_methodology/pch-smr/baseline/employment_factors_model_default_2024_2055.csv --old-mapping backend/reports/employment_methodology/pch-smr/baseline/employment_factors_mapping.yaml --old-assumptions backend/reports/employment_methodology/pch-smr/baseline/technology_assumptions_2024.csv --output-dir backend/reports/employment_methodology/pch-smr
python backend/scripts/validate_employment_factor_delivery.py --source-repo ../colombia-employment-factors --rebuild-dir ../colombia-employment-factors/output/pch-smr-rebuild
```

The last command's rebuild directory is created by running the canonical
builder with `--require-solar-ratios --output-dir output/pch-smr-rebuild`.
Run source tests explicitly with `python -m pytest tests`, keeping generated
review/cache directories out of test discovery.

The `pch-smr/` report directory contains the frozen old snapshot/mapping,
the mapping-aware 2024–2055 coefficient comparison, model employment comparison,
catalogue additions, observed construction-cohort totals and checksums. Existing
central/low/high/source-refresh reports outside this directory are historical
pre-PCH/SMR comparisons and are not relabelled as current results. The original
workbook remains the preserved source of identical deployment in both replays.

There are 2,999 blank exported capacity cells; both replays exclude them rather
than inventing zero capacity. These limitations prevent claiming a complete
reconstruction of original solver outputs. Missing derived scheduling rows,
if introduced by changed construction duration, are separately identified in
`record_presence`, with only their counterpart derived employment set to zero.

Scientific references, original links, table/page details, raw/effective
definitions and limitations are maintained in the canonical
[methodology](https://github.com/DEA-GE/colombia-employment-factors/blob/pch-smr-employment-factors/docs/methodology.md).
OECD NEA/IAEA (2018) supplies conventional-nuclear context, not validation for
SMR-specific labour requirements. Modular manufacturing, factory assembly,
design, onsite schedules, FOAK/NOAK deployment and operating staff remain
priorities for later SMR research.
